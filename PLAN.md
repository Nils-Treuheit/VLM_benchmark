# Grounding and Vision Capability Benchmarks

**Purpose:** Build a compact, broad, reproducible comparison that shows what grounding VLMs can do, where they fail, and how much query-time they cost beside fast task specialists. The benchmark is a set of separate task scorecards; it is not one blended leaderboard.

**Data root:** `/mnt/HDD1/Project_Data/public_datasets/`. Dataset files, labels and per-example predictions stay local. The current run ledger and published aggregate results are in [grounding_Bench/report.md](grounding_Bench/report.md).

**Core models:** `nvidia/LocateAnything-3B` and `GroundingPI/GroundAnything-VLM`. Both are required on every benchmark row marked runnable for grounding. YOLOE-26-L is the open-vocabulary detector/segmenter anchor. YOLO26-L and YOLO26-L-seg are fast closed-vocabulary anchors when their labels match. SAM 3.1 is the promptable detection/segmentation anchor. YOLO26-L-OBB is used only for oriented boxes.

## Scope decisions

- KITTI 2D is deprioritized and is not a completion gate. Its training-derived panel adds little coverage beside COCO, HOPE and the domain-shift panels. Do not spend time on official KITTI AP_R40 unless the suite's capability goals change. No test labels are assumed.
- RF100-VL coverage means every local constituent test subset. Use up to 20 labeled images per subset, the same deterministic seed, and the same image IDs for both VLMs and YOLOE-26-L. The five older domains remain historical pilot results and do not count as all-subset coverage.
- Run SAM 3.1 segmentation and report mask metrics only where the source dataset provides valid instance masks. A model returning masks does not create ground truth.
- A benchmark row is complete only when all required models have the same eligible items, a valid task output/evaluator, and reported failures. Attempt count alone is not successful benchmark coverage.
- Keep task scorecards separate. Do not combine referring expressions, GUI points, object boxes, masks, OCR, VQA and oriented boxes into one accuracy rank.

## Measurement contract

1. Use a fixed shared item manifest, prompt, category mapping, input size policy and evaluator for each model comparison. Record dataset source, split, license/terms, sample seed and exclusions.
2. Measure each query after the model is loaded and ready. Report model/service startup and initial checkpoint load duration separately. Do not include either in query-response time.
3. Report query mean, median, p95 and maximum, throughput, peak whole-device VRAM, completion count, parser failures, empty outputs and model/runtime identity. For generation, also report tokens/s and truncation.
4. Keep timing scope explicit. Prefer image-read through parsed response for every adapter. If an existing backend only measures generation or HTTP response, retain its recorded scope and mark cross-model speed ratios as indicative until rerun with matched boundaries.
5. Compare speed and quality on identical items. Show the fastest compatible specialist as an anchor. Do not use a model-load penalty to inflate per-query latency; present load time separately so deployment trade-offs remain visible.
6. Run only one local model on the GPU at a time. Before each local GPU probe or inference job, run `python3 .agentic_workflow/src/executor.py release-local` from this checkout and confirm managed resources are released.
